本文汇总已确认业务和粗原型，不新增产品决策。本轮只交付业务规格，明确页面、状态与验收范围，不拆开发任务。验收入口已于本轮获得用户确认，按 to-spec 标记 ready-for-agent。该状态表示规格可用于后续实施工单拆分，不代表正式产品已通过验收，或已授权开始开发。

## Problem Statement

两位伴侣需要共同安排家务、看见彼此真实的付出，并把感谢转化为双方认可且可以兑现的心愿。仅靠口头分工容易忘记本次由谁做、周期何时继续、临时接手是否改变后续轮流；补记和更正还容易让完成记录、贡献比例与可消费余额混淆。

首版需要提供从家庭建立、分工、本人打卡、感谢到心愿兑换与关闭的完整路径，尊重双方自行约定的分工，不把五五开当成目标。平台运营者需要管理公共内容、必要的家庭状态与汇总指标，同时保持家庭私有内容的访问边界。

## Solution

提供面向两位伴侣的微信小程序和面向平台运营者的电脑浏览器后台。小程序采用已确认的 B「家庭首页」：首页进入任务大厅、协作天平、动态打卡簿和心愿集市，底栏为家庭首页与家庭设置。后台沿用按角色展示的左侧导航、独立家庭详情及模板发布对照。

家务安排与本次执行分开，按固定日历生成可处理事项；实际完成人始终用本人账号打卡。有效完成同时形成贡献与可用积分，兑换消费只影响可用积分。天平采用 B「双方对照」布局表达自然月内双方的真实贡献。心愿由兑现人确认开放，兑换后由兑换人确认收到，未关闭时任一方可取消并退回原实扣积分。

现有粗原型是流程、布局、操作分层和已确认文案的依据。规格初稿之后可基于现有可操作原型进入实施工单拆分，页面细化和已决路径的缺漏在正式实现中补齐；业务语义或已确认路径发生实质变化时须单独记录并确认。

## User Stories

以下按“作为……，我希望……，以便……”组织；均受后文资格、日期、状态和权限约束。

1. 作为首次使用者，我希望创建自己的家庭，以便开始记录家务协作。
2. 作为单人家庭成员，我希望先安排家务、本人打卡并积累积分，以便不必等待伴侣加入才能开始。
3. 作为邀请人，我希望分享有效的家庭邀请并能撤销重发，以便邀请正确的伴侣加入。
4. 作为受邀人，我希望先看清邀请人和家庭再确认加入，以便主动决定建立哪一段协作关系。
5. 作为已有当前家庭的成员，我希望冲突邀请明确提示，以便不会误覆盖现有家庭关系。
6. 作为家庭成员，我希望双方平等管理家庭安排、本人维护昵称头像，以便称呼不变成权限差异。
7. 作为家庭成员，我希望在首页看见四个模块入口，以便快速进入需要的协作环节。
8. 作为家庭成员，我希望从任务大厅统一添加家务，并在预设与自行创建间保留输入，以便低成本建立适合本家的安排。
9. 作为家庭成员，我希望全选或部分选择六区预设并核对周期、分值、分工和首次日期，以便明确将添加哪些安排。
10. 作为家庭成员，我希望重复选用时跳过同源家务且保留家庭修改，以便不生成重复任务或丢失已有约定。
11. 作为家庭成员，我希望主动复制并分别命名确需多份的家务，以便区分主卧、次卧等不同事务。
12. 作为家庭成员，我希望分别查看当前待办、未来预览和全部家务，以便分清这一次执行与长期安排。
13. 作为家庭成员，我希望组合筛选区域、负责人、周期并搜索名称和说明，以便找到当前视图内的事项。
14. 作为家庭成员，我希望采用每天、指定星期、间隔天数、间隔月份或一次性计划，以便适配不同家务频率。
15. 作为家庭成员，我希望周期按原日历继续且逾期不持续积压，以便看清现在真正需要处理的事项。
16. 作为家庭成员，我希望提前完成最近一期但保留原计划归属，以便灵活安排且不重复获得完成或积分。
17. 作为家庭成员，我希望仅修改本次执行日期或分工，以便处理临时变化而不改变长期安排。
18. 作为家庭成员，我希望修改后续周期前看到保留本次、新第一次和负责人，以便理解接续结果。
19. 作为家庭成员，我希望跳过一次、暂停一项和删除安排各有清晰影响，以便按实际需要结束不同范围的工作。
20. 作为家庭成员，我希望单项恢复不补造暂停期间任务，以便不会突然出现欠账。
21. 作为家庭成员，我希望将任务直接指派给本人或伴侣，以便明确本次负责人。
22. 作为家庭成员，我希望公共任务先认领再本人打卡，以便双方知道谁已承接。
23. 作为认领人，我希望可以放回公共池，以便尚未完成时重新开放承接。
24. 作为实际接手者，我希望先把本次负责人改为本人再打卡，以便记录真实付出且不改后续轮次。
25. 作为双人家庭成员，我希望周期任务按计划轮流并预览前两次安排，以便不用依赖谁先完成决定下一次归属。
26. 作为家庭成员，我希望同时认领、改派或打卡时能看到最新结果，以便旧页面不会覆盖已生效操作。
27. 作为实际完成人，我希望不填任何可选项也能本人打卡，以便快速记录完成。
28. 作为实际完成人，我希望可选填写心得、感谢和实际完成日期，以便表达付出而不增加耗时填报。
29. 作为打卡人，我希望成功后留在原任务视图并保留筛选、显示积分与简单撒花，以便继续处理家务。
30. 作为家庭成员，我希望主动查看新动态，以便了解谁完成了什么及相关留言。
31. 作为漏记的实际完成人，我希望从“补上打卡”找到符合资格的未完成历史，以便补录自己当时已完成的家务。
32. 作为补记人，我希望可以不填实际完成日期且看到明确统计说明，以便不被要求编造日期。
33. 作为原打卡人，我希望更正或清空文字、调整实际日期并留痕，以便纠错且不重复计分。
34. 作为原打卡人，我希望填写原因撤销自己的记录并预知积分与家务去向，以便安全纠正整条错误。
35. 作为伴侣，我希望对有效记录比心或取消比心，以便表达感谢而不改变积分。
36. 作为家庭成员，我希望清楚区分贡献积分和可用积分，以便花分不会抹掉已做家务的付出。
37. 作为家庭成员，我希望查看双方流水及关联更正原因，以便追溯余额变化。
38. 作为余额因撤销变负的成员，我希望仍能纠错且看到如何抵补，以便账目保持真实。
39. 作为家庭成员，我希望按自然月查看贡献、占比、次数与记录，以便理解这一阶段双方的投入。
40. 作为家庭成员，我希望天平真实呈现差异而不催促或排名，以便尊重本家的分工约定。
41. 作为家庭成员，我希望零贡献、单方贡献和等待伴侣分别表达，以便不会把没有数据误认为各占一半。
42. 作为心愿提出人，我希望创建或选用服务建议并明确兑现人，以便先形成可协商的意向。
43. 作为兑现人，我希望本人确认内容和价格后才开放兑换，以便平台推荐不自动成为我的义务。
44. 作为兑换人，我希望兑换前核对内容、兑现人、价格和扣分后余额，以便清楚接受约定。
45. 作为兑换人，我希望余额不足或同一心愿仍待兑现时得到明确提示，以便避免无效或重复兑换。
46. 作为家庭成员，我希望心愿改价、下架或移除后旧兑换仍保留原约定，以便承诺不会被目录变化覆盖。
47. 作为兑换人，我希望收到服务后通过再次确认盖章完成，以便明确关闭这笔约定。
48. 作为家庭任一方，我希望待兑现时可主动取消并退原实扣积分，以便无需对方响应也能关闭未完成约定。
49. 作为家庭成员，我希望家务特权与实际家务分别处理，以便免洗碗约定不会自动伪造打卡。
50. 作为家庭成员，我希望明确失败保留输入、结果不明先查询，以便重试不重复记账或反馈成功。
51. 作为被停用家庭成员，我希望看到原因时间并能查历史和本人退出，以便理解当前可执行的操作。
52. 作为恢复使用的家庭成员，我希望沿有效日历继续并保留原单项暂停，以便恢复不会重建已关闭任务。
53. 作为决定退出的成员，我希望二次确认结束全家协作并自动收尾待兑现，以便退出不被余额或未履约阻止。
54. 作为原家庭成员，我希望查看归档历史并能回到当前家庭，以便保留旧记录又不混淆新旧协作。
55. 作为新家庭成员，我希望从零开始且新伴侣不能读取旧家记录，以便家庭间数据独立。
56. 作为家庭成员，我希望跨一年仍能找到历史月份、完成、未完成与积分流水，以便长期记录持续可用。
57. 作为运营管理员，我希望维护公共家务预设与默认特权模板，以便向家庭提供具体、可调整的建议。
58. 作为模板维护者，我希望区分草稿、当前发布内容和未发布修改，以便保存编辑不会直接改变家庭选用内容。
59. 作为模板维护者，我希望发布前校验并预览、下架后明确选择重发内容，以便控制公共内容何时生效。
60. 作为平台运营者，我希望查看七项全平台汇总指标及其统计口径，以便判断组建、协作与兑现情况。
61. 作为超级管理员，我希望仅用必要家庭资料进行单户停用恢复，以便处理异常而不进入私有内容。
62. 作为超级管理员，我希望管理固定角色账号且保留最后一名有效超管，以便平台权限持续可管理。
63. 作为管理员，我希望独立账号登录并在默认密码阶段先设本人密码，以便按已确认账号路径取得业务访问能力。
64. 作为遗失凭证的管理员，我希望通过对应责任人线下核实后恢复既有账号，以便恢复访问且不改变角色和停用状态。
65. 作为管理员，我希望改密、停用、角色变化及会话过期后及时重新登录，以便旧会话不继续行使失效权限。
66. 作为管理员，我希望按角色查看不可改删的操作记录，以便追溯模板、家庭及账号操作且不暴露密码或家庭私密信息。

## Implementation Decisions

本节记录业务模块边界、状态、交互及一致性要求，不决定技术栈、存储方案、接口协议或开发任务。各项完整条件及数字、日期场景与 Further Notes 的决议来源共同构成本规格。

### 1. 角色、身份与家庭生命周期

- 首版家庭最多两位伴侣，可单人起步；先生、太太仅为可修改称呼。双方平等，无家主、踢人或代打卡能力。个人昵称和头像由本人修改，双方均可修改家庭名称与安排。
- 一个个人账号同时只属于一个尚未归档的当前家庭，停用仍占名额；本人身份由账号确定。平台管理员为独立账号身份。
- 普通欢迎页只提供创建家庭；受邀人从微信分享卡片进入详情并主动确认加入。邀请有效 24 小时，可撤销或重发，成功使用后失效；过期、撤销、满员、已有当前家庭及归档均不能错误建立关系，重复提交不新增成员。
- 单人可以安排家务、本人打卡并正常积累两类积分，伴侣加入后不补发、不清零。不存在的伴侣不能被指派；轮流、伴侣比心与伴侣承诺兑换等待双人资格。

| 家庭状态或变化 | 可见和可执行结果 |
| --- | --- |
| 使用中 | 按成员资格协作；单人可先用，双人开放适用能力 |
| 使用中 → 停用 | 超管填写双方可见原因并再次确认，整户协作写入暂停；关系、余额、待兑现及停用前待办保留，不退款 |
| 停用 | 可登录、查看本人有权历史并本人退出；暂停邀请加入、设置修改、家务、打卡纠正、比心及心愿兑换处理；显示原因时间，无反馈或客服联系入口 |
| 停用 → 使用中 | 仅超管单户手动恢复；按日历衔接，不新建关系、不重新发分；邀请原有效期不延长 |
| 使用中／停用 → 归档 | 任一成员本人退出，告知影响并二次确认，无需伴侣批准；全家结束协作，另一方在小程序获知结果 |
| 已归档 | 首版不可恢复或接纳新成员；原成员可读历史，未完成待办以家庭归档关闭并保留分工、不记漏做；停止后续安排和轮流 |

- 退出不受正、负余额或待兑现阻止；待兑现自动取消并退原实扣积分至原兑换人归档钱包，已完成不退、已取消不重复退。归档余额及账目仅可查看，不可消费或迁移。
- 双方可以另建或加入新家庭，即使原两人重组也从零开始。旧家记录只供原成员查看，新伴侣不可访问；归档历史访问不占当前家庭名额。

### 2. 家务、分工与计划日历

- 公共家务预设、家庭家务、本次待办、未来预览是不同概念。选用形成独立家庭安排，完成一次不删除长期家务。固定六区为厨房烹饪、客厅公共区、卧室衣物、卫浴清洁、阳台宠植、综合事务；每项只归一区，跨区归综合事务，无自定义区域。
- 家务只设置名称、完成范围说明、区域、计划、分工和家务分值等已决内容；无耗时或独立难度属性。分值为 10～100、每档 10 分，双方可改且变更可见。
- 分工包括指派本人、指派伴侣、公共待认领、两人轮流。指派直接生效，无接受审批。两人轮流仅用于双人家庭的周期家务；每次启用选择首位并展示生效后的前两次，当前已固定一次不变。
- 公共待办先认领再本人打卡，认领不计分；认领人可放回公共池。双方可调整未完成分工、跳过或暂停，无伴侣审批；先说明影响，再让双方看到变更。伴侣本次由本人实际做时，先“本次由我接手”，再本人打卡。
- 轮流按有效计划次序，不按完成次数；接手、提前完成、跳过、逾期或撤销不补偿或重排轮次。公共周期旧次到接续日收尾后，新一期按已生效长期分工生成；若仍为公共则重新待认领。逾期本身不解除认领，一次性继续保留负责人。

| 日期概念 | 含义与边界 |
| --- | --- |
| 计划日期 | 原定执行日期，单次改期仍保留 |
| 本次执行日期 | 当前约定执行日，决定到期和逾期；不是实际完成日 |
| 接续日期 | 当前一次与下一次边界；通常为下一期计划日，改长期周期后为最后确认的新计划第一次 |
| 实际完成日期 | 可选填写的实际发生日；不能晚于今天或早于本人加入家庭日 |
| 贡献统计日 | 有实际完成日用该日，无则用原打卡／补记提交日；不补造实际完成事实 |

- 统一北京时间，仅安排日期、不填写具体时刻；执行日结束后才逾期。支持每天、每周多选星期、每隔 N 天、每隔 N 个月指定日、一次性。月末无指定日则取当月末日，以后仍用原指定日。
- 创建或载入只从今天或未来开始，不补造创建前任务。每天默认今天，可选未来；每周取不早于开始日的首个指定星期；间隔天数以首次日为起点，间隔月份以首次月份及指定日为起点，首次实际日不能早于今天。
- 长期日历不随实际完成顺延。周期旧次到接续日仍未完成则转未完成历史，不积压当前待办；一次性无下一期，继续逾期直到适用完成或关闭操作。
- 单纯浏览未来不固定安排；到计划日，或对可操作最近一期成功认领、接手、单次修改、跳过、提前完成后，该次固定。长期编辑只能替换未固定未来，不能覆盖已固定本次或已收尾历史。
- 有当前未完成待办先处理当前，只能提前操作最近一期。提前完成仍属原次、原日期不再重复要求完成；更后一期至少等原计划日和本次执行日较晚者结束后才开放，且当前仍未完成时不越过它。
- 仅修改未完成本次可改名称、说明、区域、分值、负责人、执行日期；不改长期重复或后续分工。执行日只可今天或未来，周期须早于接续日，不能同日或跨过接续日；一次性无下一期限制。
- 修改长期安排默认仅影响后续新待办，当前与历史保持。新计划第一次不得早于今天，且须晚于需要保留本次的原计划日和执行日，并符合新重复规则；无须保留本次可从今天开始。尚受提前开放限制的已完成／跳过本次也保留。
- 保存长期周期前显示保留哪次、旧次何时收尾、新第一次及负责人和下一次安排。新第一次取代旧接续日；反复改计划仅替换未固定未来，不借单次改期自动推迟接续日或重开历史。
- 保持轮流且有保留本次时，新第一次接续原计划轮次，实际被谁接手不改变；无保留本次时沿有效日历下一轮，首次轮流尚未开始则保留已选首位。被替换的未固定预览不占轮次。

| 操作或边界 | 待办和历史结果 |
| --- | --- |
| 跳过本次 | 记录已跳过，不完成、不计分，后续周期不变 |
| 暂停一项家务 | 关闭当前未完成并注明暂停；期间不生成、不记漏做、不补发 |
| 单项恢复 | 已暂停关闭、完成、跳过的本次不重开，同日反复操作也不重建；当天为原计划日且该次从未生成才生成一次，否则沿未来计划 |
| 删除家务 | 说明影响并确认；停止未来，当前未完成取消，历史打卡和积分保留 |
| 平台恢复且未跨停用前最后确认的接续日 | 恢复原未完成，保留改期、认领、分工及提前固定结果 |
| 平台恢复且已到接续日 | 旧次按平台停用关闭，不记漏做；恢复日为计划日且该次不存在才生成一次，不补发期间各次 |
| 平台恢复中的其他保护 | 单项暂停不解除；完成、跳过、暂停关闭不重建；提前完成及后一期开放限制保留；一次性已有未完成仍可恢复 |
| 暂停／停用期间的轮流 | 沿当时有效日历推算，不生成欠账，不从最后实际完成人重新开始，恢复本身不额外占轮次 |
| 一次性尚未生成且唯一日期已在暂停／停用期间过去 | 显示“日期已过，未生成待办”，不补造或记可补记历史；需要另建。恰在首次日恢复且从未生成可生成一次 |
| 一次性已因单项暂停关闭 | 恢复不重开；与平台停用保留已有一次性待办不同 |
| 重复方式切换 | 可在周期方式间修改；一次性与周期不直接互转，结束旧安排另建并保留历史 |

### 3. 本人打卡、动态与积分

- 打卡表单无必填：心得、感谢、实际完成日均可不填；正常打卡默认当天且可修改或清空，历史补记可留空。本人提交即生效，无伴侣审批；无身份切换、代打卡、耗时、评论区。
- 当前或逾期待办按当前分工完成；周期更替留下的未完成历史从独立补记入口操作，不恢复当前待办。历史原属伴侣或公共池时，本人确认“这次实际由我完成”，保留原计划归属并记录本人为实际完成人。
- 历史补记表示补录该次关闭前已做过的家务；不补造不存在任务。使用中无固定补记天数限制；已有有效完成、已跳过、暂停／删除关闭、归档均不可新增补记，停用期间也不可写。
- 同次最多一条有效完成，打卡状态、贡献和入账结果必须一致。重试及并发补记不得重复完成、计分、次数或撒花。分工变更先成功则旧打卡提示分工已更新；打卡先成功则后续接手改派不能改已完成。
- 动态仅本家可见，按提交时间倒序；展示实际完成人、分值、计划／提交／适用实际日期。补记位于新提交的位置且有标识，无日期时不推测日期。
- 本人可编辑／清空文字或更正／清空实际日期，保留“已编辑”及痕迹和已有比心；不新增完成或再撒花。不能直接改实际完成人、对应任务或已完成分值。
- 仅原打卡人可撤销，原因必填、双方可见，无固定天数限制，无需审批。确认前说明扣分、余额与家务去向；成功保留已撤销记录。伴侣不能更改或撤销对方记录。
- 撤销时接续日已到、后一期已固定或原为历史补记，均回未完成历史；单纯浏览后一期不算固定。仍可处理且未被暂停／删除等关闭时恢复原待办，保留单次修改、负责人为撤销前完成人；后续轮次不变。暂停、删除和已收尾历史不重开，停用／归档不可撤销。
- 仅伴侣可给有效完成比心，每条最多一个，可取消，不加分；重复点击最终一致。撤销后原比心只读留在旧记录，重新打卡不继承；归档后不可互动。

| 积分事件 | 贡献与次数 | 可用积分 |
| --- | --- | --- |
| 有效完成／补记 P 分 | 对应贡献统计日增加 P、次数加一 | 提交成功时加 P；提前完成不等计划日 |
| 兑换实扣 R 分 | 不变 | 减 R，不向兑现人转账 |
| 合法取消兑换 | 不变 | 向原兑换人退原实扣 R，一次 |
| 撤销原打卡 | 从撤销前归属统计期扣原获 P、次数减一 | 扣原获 P，可因纠错出现负数 |
| 更正或清空日期 | 只移动该有效记录的统计归属；清空回原提交日，不是编辑当天 | 不变；累计贡献也不变 |
| 文字更正／比心／认领／跳过 | 不变 | 不变 |

- 新家庭两类积分从零开始，不因跨日、跨月或未使用清零。贡献累计等于本家本人有效完成分值之和；可用余额为完成入账减撤销、减兑换、加取消退分。负可用积分不视为负贡献。
- 所有分工方式同分同得，无公共奖励；普通／提前打卡用本次分值，历史补记用历史保留分值，长期改价不追改已完成。
- 有实际完成日按该日归贡献；无则按原提交日并说明“未填完成日期，按记录日期统计”。跨月更正仅移贡献，撤销从原归属月扣回，不在撤销当天制造负贡献。
- 余额不足不得新增兑换，但不能阻止撤销，已有兑换不自动取消或追回；后续完成或退分抵补负余额。改已完成分值须原打卡人撤销，若恢复可处理待办再单次改分并本人打卡；若回历史仍按旧分值补记。
- 双方可查彼此在本家贡献、可用余额及完整流水：发生时间、来源、增减、操作后余额、适用更正原因。贡献日期与入账时间分开；原流水保留，撤销和退分用关联后续记录表达。无转赠、借分、任意手工加减或跨家庭追偿。

### 4. 协作天平

- 默认北京时间本自然月，支持已有记录的历史月份。信息顺序固定为月份、双方并排贡献数字、天平、温暖提示、该月家务记录；显示贡献、整数占比及辅助完成次数。
- 总贡献大于零时按双方真实贡献占总和计算比例，显示整数百分比且互补为 100%；几何倾斜使用实际比例，贡献多的一侧下沉，差值占总和线性映射、最大 13 度，相等居中。
- 不设目标比例或达标判断，不要求五五开，不使用落后、催促、惩罚或排名表达。保留“每一份付出，都有重量”“分工可以不同，每一份付出都值得被看见”等已确认温暖表达。
- 双方零贡献：0 分、0 次、占比“—”、居中，提示所选月无记录，不显示 50/50。单方有贡献：100/0，保留零贡献成员。单人：本人贡献与邀请入口，不显示双方占比，提示“你的付出，已经好好记下”。归档：历史只读。
- 可用积分和兑换明细置于积分入口，与贡献主指标区分；切月不把当前余额解释为该月余额。兑换、退分或负余额不改变贡献比例；补记、更正、撤销按已决归属同步记录、贡献与次数。

### 5. 心愿、兑换与兑现

- 首版仅兑换本家庭伴侣提供的服务或特权，不能兑换自己的承诺。双方可提出、修改、下架或移除心愿；提出人不等于兑现人。内容和价格须由兑现人本人确认才开放，未确认／拒绝不可兑换；本人提供也须明确本人确认。
- 单人可保存意向，不虚构兑现人；伴侣加入后明确并确认。价格为大于 0 的整数，不受家务十档限制，无免费兑换。
- 内容或价格修改后暂停新兑换并重新确认；下架可由兑现人确认重开，移除无恢复入口。既有兑换保留原内容、价格、兑现人及处理历史，目录变更不取消、不追改、不退分。
- 兑换前显示约定、兑现人、价格及扣分后余额，由兑换人主动确认；已开放心愿不逐笔审批。成功扣分并建立待兑现，余额不足、资格变化或不可兑换时不成立、不扣分。同一兑换人对同一心愿最多一笔未关闭兑换，关闭后可再兑，不同心愿可并存。

| 兑换当前状态 | 操作与主体 | 唯一结果 |
| --- | --- | --- |
| 待兑现 | 兑换人“我已收到，确认完成”，再次确认 | 已完成，不再增减分；兑现人不可代盖章 |
| 待兑现 | 任一方“取消并退分”，核对原兑换人和原实扣 | 已取消，原实扣退一次，无对方审批 |
| 待兑现 | 家庭归档 | 已取消，原实扣退原兑换人归档钱包一次 |
| 已完成／已取消 | 再盖章、取消或重开 | 不允许改最终结果、不再退款 |

- 兑换只有待兑现、已完成、已取消三种状态。未盖章即使线下已提供服务仍可取消；长期无人处理保持待兑现，不自动完成或退分。无兑现人提交、待确认、申诉、取消审批、撤销盖章、部分退分或追加扣分。
- 不强制兑现日期，备注可记录协商时间，更新保留痕迹，无延期罚分。已确认待兑现卡片不放“修改备注”按钮，已有备注照常展示；正式实现需承接备注信息及已决更新行为的适用承载位置，不重开主操作布局。
- 兑换成功直接进入待兑现；卡片“我已收到，确认完成”和“取消并退分”上下排列且整行显示。完成确认告知不可撤销及退款边界，成功显示盖章反馈，失败或结果不明时不提前盖章。
- 取消、盖章、归档以先成功有效操作决定关闭结果，只退一次。改价／下架／移除先成功，旧兑换确认页需刷新核对；兑换先成功则保留原约定。结果未知先查原结果，重试不另建或重复扣退。
- 免洗碗等特权只记录线下约定，不自动改派、跳过或打卡；实际家务按接手与本人打卡处理。兑换关闭不自动撤回已经发生的家务操作。

### 6. 公共模板与家庭选用

- 公共家务预设含名称、完成范围、六区、完整建议周期、合法建议分值；默认特权模板含名称、明确服务内容、正整数建议价格，无特权分类。平台维护排序和发布状态，不指定家庭成员。
- 新建家庭可跳过预设选用，后续仍能添加，不自动全量载入。统一添加页默认预设，可同页切自行创建并保留输入／勾选；全选及取消全选位于清单上方。核对名称、周期、分值、分工、首次日，补齐计划参数后提交；默认公共待认领，主动轮流需资格及前两次预览。
- 家务同源存在则跳过，含暂停；需多份主动复制命名。特权按同源及同一兑现人去重，待确认／下架均参与；再次选用进入已有项、不覆盖或自动开放。双方可分别提供同源服务；未定兑现人的同源意向仅一项，确定时冲突须使用已有项或先移除重复意向，不自动合并。
- 已删除家务／已移除心愿可从仍已发布模板重新选用，产生新条目、不恢复旧记录；旧心愿的待兑现继续保留，新条目重新确认。平台更新、下架、重发始终不覆盖家庭副本或旧约定。
- 家务按六区分组及组内平台顺序，特权按平台顺序；排序数值越小越靠前。支持名称说明搜索，家务另有区域、周期筛选；后台两类模板均可按发布状态筛选。

| 平台模板操作 | 生效边界 |
| --- | --- |
| 新建／保存草稿 | 允许不完整，不可供家庭选用 |
| 保存已发布模板编辑稿 | 当前发布内容继续可选，保存不等于发布 |
| 发布修改 | 校验并预览家庭所见、说明影响、确认后生效，仅影响后续选用 |
| 下架 | 确认后停止新选用，保留家庭内容与编辑稿独立性 |
| 重新发布 | 明确选最后发布内容或修订后发布，不顺带发布未确认编辑稿，保留同源关系 |

- 首批公共家务至少 24 项，六区各至少 3 项，整体覆盖日常、每周重点及定期深度清洁；名称具体可独立完成，说明清楚、不过度拆分计分，养宠等适用条件明确。数量为整库验收，不是每次发布单条的前提；完整内容库尚未制作验收。
- 家庭提交前列新增、同源跳过、待修正、已下架；同源跳过可继续，其他问题先处理。预览后内容重发或下架时保留输入勾选、点明变化并重新核对，下架项先移除；仅排序变化不打断。
- 一次确认应新增项全部成功或全部不新增，已说明同源跳过不算失败。并发载入先成功家庭内容保留，另一方同源跳过，其余仍遵守整次新增一致性；重复或未知结果先查询，不能重复或覆盖。

- 普通纠错由本人按既有流程处理。系统故障仅按可证明业务事件恢复原结果并留依据、双方可查相关账目原因；无法证明不猜测补分。该原则不新增后台手工调账、客服工具或私有记录访问。

### 8. 管理员账号访问

- 使用独立唯一用户名及密码，无自助注册。初始超级管理员随基础数据初始化，由维护人员交付首次登录信息；后续账号由超管按固定角色开通并向本人交付。用户名创建后不可修改，停用后也不再分配他人；显示名称可改，历史归属不变。
- 初始及重置密码按已确认决议为 `123456`。默认密码登录只能进入本人设密，不能访问业务页；新密码 8～64 位、不同于默认和当前密码，两次输入一致，完成设密并成功进入后台才视为交付完成。
- 普通管理员遗失密码由超管线下核实后重置；所有有效超管均无法登录时，经维护渠道线下核实项目负责人，恢复既有账号。无线上身份审核或审批，不改变角色或停用状态。
- 重置后恢复默认密码，原凭据及全部旧会话失效；即使文字仍为默认密码也不能保留旧会话。停用账号仍停用；默认登录后再次强制设密。
- 本人主动改密需当前密码、新密码和再次确认，成功退出全部会话，用新密码重登。密码错误留登录页，连续 5 次暂停尝试 15 分钟；与账号停用区分。
- 无操作满 30 分钟或登录满 12 小时需重登；主动退出／失效回登录页，未提交业务不自动补交。账号停用后退出，角色变化后重登按最新权限，旧会话不可继续操作。
- 创建、首次改密、本人改密、重置及维护恢复全部留痕，后两者另有原因；不记录密码或线下身份材料，不借日志交付凭据。
- 重复初始化不覆盖已有账号密码角色；同次开通、改密、重置只生效一次，用户名冲突不覆盖。失败／未知不误报成功，先核对再重试；旧重置请求重复提交不得覆盖其后本人已改的密码。

### 9. 已确认页面组织与交互约束

- 小程序首页进入四模块，底栏家庭首页／家庭设置，模块可返回首页。任务大厅区分当前、未来、全部；添加入口在页头右上。详情第一层只突出适用的本人打卡／认领／接手，“调整这一次”承接单次修改、跳过、放回；全部家务进入长期管理，复制删除收进更多操作。
- 普通与提前打卡成功留原任务视图并保留筛选，显示已完成、获得分值、简单撒花；主动查看记录进入对应动态。动态顶部“以前做过，忘记打卡了？”及“补上打卡”，本人有效记录单一“修改记录”入口分流文字／日期更正和整条撤销。

- 后台按角色固定左侧导航，当前账号与角色持续可见，家庭处理用独立列表／详情及确认流程；模板编辑并排对照当前发布与本次编辑，窄屏上下排列且标题明确，已下架标为最后发布内容。预览影响，未保存离开明确选择保留或放弃；受限页面拒绝访问并提供有权返回入口，不呈现受限字段。界面组织不得增加角色或私有字段权限。

## Testing Decisions

### 验收入口与证据要求

验收入口已由用户确认（“符合，按此写入规格”）：沿用工单 12 的既有用户旅程，优先从“小程序双人协作闭环”和“后台按角色运营闭环”观察外部结果，作为一份首版验收清单的两端入口。正式实现阶段按上表核对页面、状态和交互，并在这些路径验证身份、权限、并发、日期与账目边界。此处不为每个技术模块另建测试接口或预选框架。

好的测试验证用户能做什么、看到什么和持久化后的业务结果，不断言内部函数、组件结构或实现细节。真实身份／权限、并发、日期推进和积分一致性不能用按钮隐藏、文字说明、内存模拟或一次构建成功代替；正式实现可在必要边界采用可控日期、独立会话和业务读写结果验证，具体技术承载后定。

当前仓库提供静态粗原型与定向浏览器检查记录，未发现正式产品测试套件或已确定技术栈。复用的是既有场景、入口和预期，不把原型模拟器当生产测试接口。业务模块覆盖家庭关系、家务与日历、分工、打卡和动态、积分、天平、心愿与兑换、公共模板、后台权限、账号访问及指标。
